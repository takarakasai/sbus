# S.BUS / S.BUS2 受信仕様

Rust crate `sbus` が扱う Futaba S.BUS / S.BUS2 の受信側ワイヤ仕様。

- 対象: namiashi rev2 (CH348L) の SBUS ポート = UART6 / CN2
- 物理層: 反転 TTL 100 000 bps 8E2、**受信専用**
- 実測環境: 2026-08-18、CH348L (VID 0x1A86 / PID 0x55D9) + S.BUS2 受信機
  （型番は未確認。テレメトリ挙動から R3008SB 系と推定）

> 本書の数値は原則としてすべて **上記環境での実測** に基づく。
> 実測で裏付けが取れていない箇所は §7 に「未検証」として明示的に分離してある。
> 実装時は §7 を無検証の事実として扱わないこと。

---

## 1. 物理層

| 項目 | 値 | 出典 |
| --- | --- | --- |
| ボーレート | 100 000 bps | 実測 66.5 fps / 1 712 B/s と整合 |
| フレーミング | 8 データビット / **偶数パリティ** / 2 ストップビット (8E2) | `nm_board/ch348/spec_rev2_0_0_asbuilt.md` §10 T11 |
| 論理 | 反転 TTL。基板上 U15 (74LVC2G04) がハード反転するため **ソフト反転不要** | 同 §4 |
| 方向 | 受信専用。SBUS_TX は U15 出力までで CN2 未接続 | 同 §4 |
| コネクタ | CN2 (GH 1.25mm 3pin): `1=GND, 2=+5V(給電), 3=SBUS_RX` | 同 §4 |

1 バイトは start(1) + data(8) + parity(1) + stop(2) = **12 ビット**。
100 000 bps では 1 バイト 120 µs、25 バイトフレームは 3.0 ms。

受信専用であるため、本 crate は **送信を一切行わない**。S.BUS2 のテレメトリ・
ハブ（センサをポーリングする側）にはなれない。線上を流れる応答を傍受するだけである。

## 2. 制御フレーム (25 バイト)

```
 offset  0     1                     22    23     24
        +-----+---------------------+-----+------+--------+
        | 0x0F| 16ch × 11bit = 22B  |     | flags| footer |
        +-----+---------------------+-----+------+--------+
```

| offset | 内容 |
| --- | --- |
| 0 | 開始バイト 固定 `0x0F` |
| 1..23 | 16 チャネル × 11 ビット をリトルエンディアン・ビット連結した 22 バイト |
| 23 | フラグバイト (§2.2) |
| 24 | footer (§2.3) |

チェックサムは存在しない。フレームの妥当性は「開始バイト + footer の値」でのみ
判定できる（§4 の再同期方針を参照）。

### 2.1 チャネルのビット展開

`d = frame[1..23]`（22 バイト）に対し、11 ビット値をリトルエンディアンで詰めたもの。
`ch[n]` は 0..2047。

```
ch0  = (d0        | d1  << 8)             & 0x7FF
ch1  = (d1  >> 3  | d2  << 5)             & 0x7FF
ch2  = (d2  >> 6  | d3  << 2 | d4 << 10)  & 0x7FF
ch3  = (d4  >> 1  | d5  << 7)             & 0x7FF
ch4  = (d5  >> 4  | d6  << 4)             & 0x7FF
ch5  = (d6  >> 7  | d7  << 1 | d8 << 9)   & 0x7FF
ch6  = (d8  >> 2  | d9  << 6)             & 0x7FF
ch7  = (d9  >> 5  | d10 << 3)             & 0x7FF
ch8  = (d11       | d12 << 8)             & 0x7FF
ch9  = (d12 >> 3  | d13 << 5)             & 0x7FF
ch10 = (d13 >> 6  | d14 << 2 | d15 << 10) & 0x7FF
ch11 = (d15 >> 1  | d16 << 7)             & 0x7FF
ch12 = (d16 >> 4  | d17 << 4)             & 0x7FF
ch13 = (d17 >> 7  | d18 << 1 | d19 << 9)  & 0x7FF
ch14 = (d19 >> 2  | d20 << 6)             & 0x7FF
ch15 = (d20 >> 5  | d21 << 3)             & 0x7FF
```

`ch0..ch7` が `d0..d10`、`ch8..ch15` が `d11..d21` に閉じている点に注意
（8 チャネル = 88 ビット = 11 バイトで、前半後半が独立している）。

### 2.2 フラグバイト (offset 23)

| ビット | マスク | 意味 |
| --- | --- | --- |
| 0 | `0x01` | ch17 (デジタル) |
| 1 | `0x02` | ch18 (デジタル) |
| 2 | `0x04` | frame_lost — 受信機が RF フレームを取りこぼしている |
| 3 | `0x08` | failsafe — 受信機がフェイルセーフ動作中 |
| 4-7 | `0xF0` | 未使用（実測では常に 0） |

送信機の電源を落とすと `0x0C`（frame_lost + failsafe 同時）になる（§6.2）。

### 2.3 footer バイト (offset 24)

| 値 | 意味 |
| --- | --- |
| `0x00` | S.BUS1 (テレメトリなし) |
| `0x04` | S.BUS2 / スロットグループ **0** |
| `0x14` | S.BUS2 / スロットグループ **1** |
| `0x24` | S.BUS2 / スロットグループ **2** |
| `0x34` | S.BUS2 / スロットグループ **3** |

グループ番号 = `(footer >> 4) & 0x03`。下位ニブルの `0x4` が S.BUS2 の印である。

実測（8 秒 / 532 フレーム）では `0x04 → 0x14 → 0x24 → 0x34` を厳密に循環し、
`0x00` は 1 度も現れなかった。

### 2.4 raw ↔ µs 換算

S.BUS の raw 値 172–1811 が概ねパルス幅 1000–2000 µs に対応する。

```
us = round((raw - 172) * 1000 / 1639) + 1000
```

これは慣用の近似式であり、受信機/送信機のエンドポイント設定に依存する。
表示補助以外の用途（制御入力など）には raw 値をそのまま使うべきである。

## 3. フレームレートとタイミング（実測）

| 項目 | 実測値 |
| --- | --- |
| フレームレート | 66.5 fps（周期 15.0 ms） |
| バイトレート | 1 712 B/s |
| フレーム送出時間 | 3.0 ms（25 B × 120 µs） |
| スロット応答の遅延 | 制御フレーム終端から **約 2.3 ms 後** |

15 ms 周期は S.BUS の「アナログモード」に相当する。
1 サイクル = 4 フレーム = 約 60 ms で footer が 1 周する。

タイミング上の含意: **制御フレームを受信した時点ではスロット応答はまだ線上に無い。**
フレームとスロットを 1 回の read で同時に取得できると仮定した実装は破綻する。
到着順に処理するストリームパーサが必要である（§4）。

---

## 4. ストリーム構造と再同期

S.BUS2 のストリームは、制御フレームとスロット応答が交互に現れる。

```
0F F9 5B DF ... 02 10 80 00 04   03 C0 31     ← group0 フレーム + スロット応答
0F F9 5B DF ... 02 10 80 00 14                ← group1 (応答なし)
0F F9 5B DF ... 02 10 80 00 24                ← group2 (応答なし)
0F F9 5B DF ... 02 10 80 00 34                ← group3 (応答なし)
0F F9 5B DF ... 02 10 80 00 04   03 C4 F1     ← 次サイクル、値が交替
```

チェックサムが無いため、同期には以下の性質を利用する。

1. **制御フレームの判定**: `buf[0] == 0x0F && buf[24] ∈ {0x00,0x04,0x14,0x24,0x34}`。
2. **スロット応答の判定**: 直前に S.BUS2 フレームを消化しており、かつ
   `buf[0]` が有効なスロット ID（§5.1）であること。
3. **ID 空間の非衝突**: 有効なスロット ID は 256 通り中ちょうど 32 個で、
   ビットパターン `0b_____011` に一致するものに限られる（§5.1）。
   `0x0F` は下位 2 ビットこそ `11` だがビット 2 が立っており該当しない。
   したがってフレーム先頭とスロット先頭は取り違えない。
4. **desync 時**: 25 バイト溜まった状態で 1 の条件を満たさなければ先頭 1 バイトを捨てる。
   このときスロット受付状態も解除する（グループ文脈が信用できないため）。

この方針により、スロット応答を「ゴミバイト」として捨てずに済む。
実測での検証: 5 秒間で desync 0 バイト / フレーム 332 / スロット応答 83。

## 5. S.BUS2 テレメトリスロット

### 5.1 スロット応答フォーマット

1 スロット = **3 バイト**。

```
+---------+--------+-------+
| slot ID | data0  | data1 |
+---------+--------+-------+
```

1 グループは 8 スロットに対応するため、1 フレーム後に最大 8 応答（24 バイト）が続き得る。
全 4 グループで最大 32 スロット。

スロット ID は **スロット番号の下位 6 ビットをビット反転して 2 ビット左シフトし、
下位 2 ビットに `11` を置いた値**である。

```
slot_id(n) = (reverse_bits_6(n & 0x3F) << 2) | 0b11
```

| slot | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| group 0 | `03` | `83` | `43` | `C3` | `23` | `A3` | `63` | `E3` |
| group 1 | `13` | `93` | `53` | `D3` | `33` | `B3` | `73` | `F3` |
| group 2 | `0B` | `8B` | `4B` | `CB` | `2B` | `AB` | `6B` | `EB` |
| group 3 | `1B` | `9B` | `5B` | `DB` | `3B` | `BB` | `7B` | `FB` |

32 個すべて一意であることを確認済み。またこの 32 個は
**`id & 0b111 == 0b011` を満たすバイトと過不足なく一致する**（256 通りを全探索して確認）。
ビット 2 が立つ値（`0x07`, `0x0F`, …）はビット反転後にスロット番号 32 以上を指してしまうため
無効であり、これが開始バイト `0x0F` を ID 空間から排除している。

> 実測で観測されたのは **slot0 (`0x03`) のみ**。他の 31 個は上式から導いた値であり、
> 実機で確認していない（§7）。

### 5.2 slot0 = 受信機内蔵電圧計 (Rx-Batt / Ext-Volt)

slot0 には受信機自身が 2 系統の電圧を **1:1 で交替させて** 載せる。

```
+------+--------+-------+
| 0x03 | marker | value |
+------+--------+-------+
```

| marker | 系統 | 送信機での表示名 |
| --- | --- | --- |
| `0xC0` | 受信機電源電圧 | Rx-Batt |
| `0xC4` | 外部電圧入力 | Ext-Volt |

`value` は **0.1 V / LSB** の符号なし 8 ビット値。

```
volts = value as f32 * 0.1
```

#### 確定の根拠

送信機のテレメトリ表示と実測バイト列を突き合わせた。

| 生バイト | value | 本式 | 送信機表示 |
| --- | --- | --- | --- |
| `03 C0 31` | `0x31` = 49 | 4.9 V | Rx-Batt **4.9 V** ✓ |
| `03 C4 F1` | `0xF1` = 241 | 24.1 V | Ext-Volt **24.1 V** ✓ |

補強証拠:

- 10 秒 / 166 応答で、marker `0xC0` と `0xC4` が **83 回ずつ厳密に 1:1 交替**した。
  1 スロットに 2 系統が多重化されていることの裏付け。
- marker バイトは 83 サンプル全てで完全固定、`value` バイトのみ `0xF0`/`0xF1` と ±1 揺れた。
  値が `value` 側にあることの裏付け（もし marker 側に値の上位ビットがあれば、
  そちらが揺れるか、少なくとも揺れの配分が変わる）。
- Rx-Batt 4.9 V は CN2 pin2 の +5V 給電で受信機を駆動している構成と整合する。

#### 棄却した解釈

`value` を 12 ビット `((marker & 0x0F) << 8) | value` と読む案は、
Ext-Volt が 12.64 V となり送信機表示 24.1 V と一致しないため棄却。
また同案では Rx-Batt が 0.49 V となり、こちらも成立しない。

## 6. 実測ログ（一次データ）

`crates/sbus-protocol/tests/fixtures/` に生バイト列を保存してある。
送信機の電源が無い状態でも回帰テストが回るようにするためである。

| ファイル | 内容 |
| --- | --- |
| `sbus2_linked_3s.bin` | 送信機 ON。3 秒 / 5 126 B / 199 フレーム / 50 スロット応答 |
| `sbus2_failsafe_8s.bin` | 送信機 OFF。8 秒 / 13 700 B / 532 フレーム / 133 スロット応答 |

チャネル値は両者とも概ね以下（スティック静止）。

```
CH 1017 1006 1035 1014   64   64 1984 1984   64 1984 1024 1024 1024 1024 1024 1024
```

CH5/CH6/CH9 = 64、CH7/CH8/CH10 = 1984 はスイッチ類の両端値、
CH11-16 = 1024 は未割当チャネルの中央値である。

### 6.1 リンク正常時 (`sbus2_linked_3s.bin`)

`frame_lost = 0`、`failsafe = 0`。Rx-Batt 4.9 V 固定、Ext-Volt 24.0–24.1 V（1 LSB 揺れ）。
送信機のテレメトリ表示は Rx-Batt 4.9 V / Ext-Volt 24.1 V。

### 6.2 送信機 OFF 時 (`sbus2_failsafe_8s.bin`)

送信機の電源を落とした状態で採取した。観測された挙動:

| 項目 | 結果 |
| --- | --- |
| フレーム送出 | **継続**。66.5 fps のまま変わらない |
| `failsafe` | 全 532 フレームで **1** |
| `frame_lost` | 全 532 フレームで **1**（フラグバイト = `0x0C`） |
| チャネル値 | **直前の値を保持**。0 やニュートラルには落ちない |
| footer 循環 | 変化なし（0→1→2→3） |
| テレメトリ | **継続**。Rx-Batt 4.9 V、Ext-Volt 24.0 V |

テレメトリが継続する点が重要である。slot0 の 2 系統は受信機自身が測っている値であり、
RF リンクの状態とは独立している。逆に言えば、**テレメトリが取れていることは
送信機と繋がっていることの証明にはならない**。リンクの生死は `failsafe` /
`frame_lost` フラグで判定すること。

## 7. 未検証事項・既知の制約

実装はこれらを「不明」として扱い、黙って推定値を返してはならない。

1. **25.5 V 超の Ext-Volt**
   `value` が 8 ビット 0.1 V/LSB なので表現上の上限は 25.5 V。実測できた最大は 24.1 V で
   上限の直下である。これを超えたときに marker 側へ上位ビットが乗るのか、飽和するのかは
   **未検証**。→ 実装では未知 marker を捨てずに `Unknown` として上位へ渡し、
   カウントできるようにする。

2. **slot1 以降のスロット ID**
   §5.1 の表は式から導いた値で、実機では slot0 のみ観測。外部テレメトリセンサ
   （SBS-01V 等）を接続した検証ができていない。

3. **slot0 以外のデータ意味**
   スロット番号ごとのセンサ種別・スケールは一切不明。

4. **S.BUS1 (footer `0x00`) の実機確認**
   本環境では観測されなかった。デコード経路は実装してあるがフィクスチャが無い。

5. **frame_lost 単独の状態**
   `failsafe` と `frame_lost` が同時に立つケース（送信機 OFF）は §6.2 で確認済みだが、
   `frame_lost` のみが立つ状態（電波が弱く取りこぼしはあるがフェイルセーフには
   至っていない）は再現できていない。ビット演算のみなので単体テストで代替している。

6. **受信機の型番**
   テレメトリ挙動からの推定に留まる。marker 値やスロット割当が機種依存である可能性がある。

7. **`raw_to_us` の妥当性**
   §2.4 の通り近似式。エンドポイント設定依存。

ワイヤ解釈を持つ。Python 側が一次検証環境で、Rust 側はその移植である。
